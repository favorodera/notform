---
title: Submission
description: Understand NotForm's submit lifecycle and how validation and onSubmit work together.
---

Submission in NotForm is a small lifecycle around validation.

When `form.submit` is bound to a native form event, it prevents the browser's default navigation, validates the form, and calls your submit handler only when validation succeeds.

## Basic submission

```vue
<template>
  <NotForm
    :form="form"
    @submit="form.submit"
  >
    <!-- fields -->

    <button
      type="submit"
      :disabled="form.isSubmitting"
    >
      {{ form.isSubmitting ? 'Submitting…' : 'Submit' }}
    </button>
  </NotForm>
</template>
```

## Submission lifecycle

`form.submit()` performs these steps:

1. prevents the browser's default submit when called with an event
2. marks current fields as touched
3. synchronizes dirty state for the current form shape
4. validates the complete form
5. stores validation issues when invalid
6. calls `onSubmit` with validated output when valid
7. keeps `isSubmitting` active while `onSubmit` runs

## `isSubmitting`

Use `form.isSubmitting` to disable repeated submission or display progress:

```vue
<template>
  <button
    type="submit"
    :disabled="form.isSubmitting"
  >
    {{ form.isSubmitting ? 'Saving…' : 'Save' }}
  </button>
</template>
```

A second submit call while one submission is running is ignored.

## Successful submission

`onSubmit` receives the schema's **output** type.

```ts
const form = useNotForm({
  async onSubmit(data) {
    await saveUser(data)
  },
  schema,
})
```

This matters for schemas that coerce or transform their input.

## Invalid submission

When validation returns issues:

- the issues replace `form.errors`
- `onSubmit` is not called
- `isSubmitting` returns to false after the lifecycle finishes

Because submission marks current fields as touched, error UI can become visible on the first attempted submit.

## Programmatic submission

You can also submit from code:

```ts
await form.submit()
```

When called with a native event, `submit()` calls `preventDefault()` immediately.

## Native form behavior

`NotForm` and `form.submit()` have deliberately separate responsibilities.

`NotForm` prevents the browser's native reset behavior and provides context. `form.submit()` prevents native submit navigation, performs validation, and runs the application callback.

This means you can also use the form instance without the `NotForm` component.

## Server errors

Server-side validation belongs to the same error state as schema validation.

After an API request fails, use `form.setError()` to attach issues to fields or to the form itself.

See [Server Errors](/docs/concepts/server-errors).

## Reset after success

NotForm does not automatically make submitted values the new clean baseline.

If your application wants the saved values to become the new baseline:

```ts
form.reset(savedValues)
```

That clears dirty and touched state and makes those values the next reset target.

---
title: Server Errors
description: Map server-side validation failures back into NotForm state.
---

Client-side schema validation catches local rules. Your server may still reject the request because a value already exists, a permission changed, or a business rule failed.

Use `form.setError()` to map those failures into the same state your field UI already reads.

## Set a field error

```ts
form.setError({
  message: 'This email is already registered.',
  path: ['email'],
})
```

The field can render it with the normal API:

```vue
<template>
  <NotMessage path="email" />
</template>
```

## Form-level errors

A server response can also belong to the whole form:

```ts
form.setError({
  message: 'The account could not be updated.',
})
```

An issue without a path is not attributed to an individual field or array.

## Multiple field errors

`setError()` upserts by path. A new path is appended; an existing path is replaced.

```ts
form.setError({
  message: 'Email is already registered.',
  path: ['email'],
})

form.setError({
  message: 'Username is unavailable.',
  path: ['username'],
})
```

## Map your API at the boundary

NotForm does not require a specific server error format. Translate your API response into Standard Schema-shaped issues in your request layer:

```ts
try {
  await saveUser(form.values)
} catch (error) {
  for (const issue of mapApiErrors(error)) {
    form.setError(issue)
  }
}
```

This keeps server-specific response formats out of the form components.

## Server errors and validation

Client validation and server errors share `form.errors`.

A later `validate()` call can replace the current error collection with the schema's result, so server errors should be treated as part of the current request state rather than permanent field metadata.

## Resetting server errors

`form.reset()` restores the baseline errors.

If a successful save should establish a new clean baseline:

```ts
form.reset(savedValues)
```

That also clears touched and dirty state.

::tip
Use the same `Issue` shape for server errors that you use for schema issues. This lets the rest of the NotForm UI stay unaware of where the error came from.
::

---
title: Form State
description: Understand values, errors, dirty state, touched state, and validation state in NotForm.
---

NotForm keeps form state in one reactive form instance.

The instance separates the data itself from the state that describes how that data is being edited, validated, and submitted.

## Values

`form.values` contains the live form input data.

```ts
const form = useNotForm({
  initialValues: {
    email: '',
  },
  schema,
})

form.values.email = 'jane@example.com'
```

Values are based on the schema's **input** type.

Nested values stay reactive:

```ts
form.values.profile.name
form.values.profile.address.city
```

## Initial values

`initialValues` establishes the starting baseline used by dirty-state comparison and `reset()`.

NotForm deep-clones the supplied initial values, so later mutations do not change the original object you passed in.

You can replace the baseline later with `reset(nextValues, nextErrors)`.

## Dirty state

A value is dirty when its current value differs from the baseline value.

The comparison is deep, so objects and arrays are compared by content instead of reference identity.

At the form level:

```ts
form.isDirty
```

For an individual field, use `isDirty` from [`NotField`](/docs/components/not-field). For an array, `NotArrayField.isDirty` includes descendants.

Changing a value back to its baseline clears the dirty state for that path.

::note
`setValue()` updates dirty state, but it does not run validation. Validation still happens through field triggers or an explicit `validate()` / `validateField()` call.
::

## Touched state

A field becomes touched when its blur handler runs or when submission marks the current fields as touched.

At the form level:

```ts
form.isTouched
```

Touched state is interaction state. It does not imply validity.

## Errors

`form.errors` contains the active validation issues.

Each issue comes from the Standard Schema validator and can optionally include a path describing where the problem belongs.

For one field:

```ts
form.getFieldErrors('email')
```

`getFieldErrors()` is an exact-path query. An issue at `profile.email.name` is not returned for `profile.email`.

This makes field errors precise while allowing aggregate components such as `NotArrayField` to reason about descendant state recursively.

## Valid state

```ts
form.isValid
```

`isValid` is derived from the current `errors` collection. It does not execute validation by itself.

A new form can therefore be `isValid` until a validation run has actually stored issues.

## Validating state

```ts
form.isValidating
```

This is true while one or more validation runs are active.

Overlapping validations are tracked independently, so the flag remains true until every active run has settled or has been invalidated by a newer form change.

## Submitting state

```ts
form.isSubmitting
```

This becomes true when `submit()` starts and stays true through validation and the async `onSubmit` callback.

A second submission while one is already running is ignored.

## Resetting state

Calling:

```ts
form.reset()
```

restores the current baseline values and errors and clears touched and dirty state.

Passing values or errors changes the baseline rather than merging into it:

```ts
form.reset({
  email: 'jane@example.com',
})
```

The supplied object becomes the complete new value baseline.

## State at a glance

| State | Meaning | Notes |
| --- | --- | --- |
| `values` | Current input data | Inferred from schema input |
| `errors` | Current validation issues | Replaced by whole-form validation |
| `isDirty` | A value differs from baseline | Deep comparison |
| `isTouched` | A field has been touched | Interaction state |
| `isValid` | No active errors | Does not run validation |
| `isValidating` | Validation is in flight | Tracks overlapping runs |
| `isSubmitting` | Submit lifecycle is active | Includes async `onSubmit` |

## Field state vs form state

Field components expose a narrower view of the same instance.

For example, the form may have one invalid email field:

```text
form.isValid       → false
email.isValid      → false
password.isValid   → true
```

The field components do not create separate validation stores. They read from the same form instance.

Continue with [Validation](/docs/concepts/validation) to see how errors and validation state change over time.

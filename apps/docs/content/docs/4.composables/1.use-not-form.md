---
title: useNotForm
description: Create and manage a typed, reactive NotForm instance.
---

`useNotForm()` creates the form instance used by the NotForm components and composables.

It connects a Standard Schema-compatible validator to reactive values, errors, interaction state, validation, submission, and reset behavior.

## Usage

```ts
import { useNotForm } from 'notform'
import { z } from 'zod'

const schema = z.object({
  email: z.email(),
  password: z.string().min(8),
})

const form = useNotForm({
  initialValues: {
    email: '',
    password: '',
  },
  async onSubmit(values) {
    await save(values)
  },
  schema,
})
```

## Signature

```ts-type
useNotForm<TSchema extends ObjectSchema>(
  config: UseNotFormConfig<TSchema>,
): NotFormAPI<TSchema>
```

## Options

| Option | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `schema` | `MaybeRefOrGetter<TSchema>` | Yes | — | Standard Schema validator |
| `initialValues` | `DeepPartial<InferInput<TSchema>>` | No | `{}` | Starting values and dirty baseline |
| `initialErrors` | `Issue[]` | No | `[]` | Errors shown before validation |
| `onSubmit` | `(data: InferOutput<TSchema>) => Promise<void> \| void` | No | — | Called after successful submit validation |

## Return value

### Values and errors

| API | Type | Description |
| --- | --- | --- |
| `values` | `InferInput<TSchema>` | Deeply reactive form values |
| `errors` | `Issue[]` | Current active validation issues |
| `getFieldErrors(path)` | `Issue[]` | Issues whose path exactly matches `path` |
| `setError(error)` | `void` | Upsert or add a validation issue |
| `setValue(path, value)` | `void` | Set a typed value at a field path |

### State

| API | Type | Description |
| --- | --- | --- |
| `isDirty` | `boolean` | Any value differs from baseline |
| `isTouched` | `boolean` | At least one field is touched |
| `isValid` | `boolean` | Current error collection is empty |
| `isValidating` | `boolean` | One or more validations are in flight |
| `isSubmitting` | `boolean` | A submission is in progress |

### Validation and lifecycle

| API | Type | Description |
| --- | --- | --- |
| `validate()` | `Promise<StandardSchemaV1.Result<InferOutput<TSchema>>>` | Validate the entire form |
| `validateField(path)` | `Promise<StandardSchemaV1.Result<InferOutput<TSchema>>>` | Validate one path scope |
| `submit(event?)` | `Promise<void>` | Touch, validate, then submit when valid |
| `reset(values?, errors?)` | `void` | Replace the baseline and reset state |

## `values`

Values use the schema's input type:

```ts
form.values.email = 'jane@example.com'
form.values.profile.address.city = 'Lagos'
```

The object is deeply reactive and can be bound directly with `v-model`.

## `setValue`

Use `setValue()` when a custom input or application code needs to update a field:

```ts
form.setValue('email', 'jane@example.com')
```

The path and value are inferred together from the schema.

Calling `setValue()`:

- updates the value
- synchronizes dirty state
- invalidates older in-flight validation
- does not run validation itself

## `errors`

`form.errors` is the shared collection used by the form and field components.

Use `getFieldErrors()` for an exact path:

```ts
form.getFieldErrors('email')
```

A nested descendant issue is not returned by a parent exact-path query.

## `setError`

Use `setError()` for server-side errors or application-specific validation:

```ts
form.setError({
  message: 'Email is already registered.',
  path: ['email'],
})
```

A second issue at the same path replaces the previous one.

## `validate`

```ts
const result = await form.validate()
```

A successful validation clears current errors and returns the schema output. A failed validation returns issues and replaces `form.errors`.

Overlapping whole-form validations are last-write-wins for shared form state.

## `validateField`

```ts
await form.validateField('email')
await form.validateField('users')
await form.validateField('users.0')
```

Parent object and array paths include descendant issues in the validation scope.

The returned value remains the schema's result; only the shared errors written by this call are scoped to the requested path.

## `submit`

Bind it to a native form:

```vue
<NotForm
  :form="form"
  @submit="form.submit"
>
  ...
</NotForm>
```

Or call it directly:

```ts
await form.submit()
```

A native event is prevented immediately. Submission then touches current fields, validates the full form, and calls `onSubmit` only when the validation succeeds.

## `reset`

Reset the current baseline:

```ts
form.reset()
```

Or establish a new baseline:

```ts
form.reset({
  email: 'jane@example.com',
})
```

You can also provide baseline errors:

```ts
form.reset(
  { email: 'jane@example.com' },
  [{ message: 'Verification required', path: ['email'] }],
)
```

Reset clears touched and dirty state and invalidates in-flight validation.

::caution
`reset(values, errors)` replaces the previous baseline. It does not merge the supplied object with the existing baseline.
::

## Input and output types

The form instance uses two related schema types:

```text
InferInput<TSchema>   → form.values / initialValues
InferOutput<TSchema>  → validate result / onSubmit
```

This distinction matters for schemas that coerce or transform data during validation.

## Reactive schema

`schema` accepts a value, a Vue ref, or a getter through `MaybeRefOrGetter`:

```ts
const form = useNotForm({
  schema: computed(() => currentSchema.value),
})
```

The validator remains external to NotForm and is never turned into a NotForm-specific schema object.

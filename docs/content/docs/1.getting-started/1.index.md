NotForm is a headless form library for Vue 3 and Nuxt.

It manages the parts of forms that tend to spread across components: values, validation errors, touched and dirty state, validation timing, submission, resetting, and dynamic arrays while not deciding what your form should look like.

You choose the inputs, labels, layout, accessibility attributes, styling, and design system. NotForm provides the reactive state and primitives that connect those pieces together.

## Why NotForm?

Forms usually become difficult for one of two reasons: the UI layer starts owning business logic, or the form logic becomes so generic that integrating it with real UI requires a lot of glue code.

NotForm keeps those concerns separate meaning that your application owns rendering while NotForm owns form state.

## The core model

A NotForm form has three layers.

- **Schema**

Your validator defines what the data means, which values are valid, and what successful output looks like.

- **Form instance**

[`useForm`](/docs/composables/use-form) holds the live values, errors, interaction state, and form lifecycle methods.

- **UI**

[`Form`](/docs/components/form), [`Field`](/docs/components/field), [`ArrayField`](/docs/components/array-field), and [`Error`](/docs/components/error) connect the form instance to your template.

This separation is the main idea behind NotForm. You can replace the validator or redesign the UI without rebuilding the form state layer.

## Schema-driven validation

NotForm does not define its own validation language. It accepts schemas that implement [Standard Schema](https://standardschema.dev/).

That gives the form engine one predictable contract for synchronous and asynchronous validation, validation issues and their paths, schema input types, and schema output types.

For example, with Zod:

```ts
import { z } from 'zod'

const schema = z.object({
  email: z.email('Enter a valid email address'),
  password: z.string().min(8, 'Password must be at least 8 characters'),
})
```

The same form architecture works with other Standard Schema-compatible validators.

Read more in [Validation](/docs/concepts/validation).

## Reactive form state

The form instance exposes state directly:

```ts
form.values
form.errors
form.isDirty
form.isTouched
form.isValid
form.isValidating
form.isSubmitted
form.isSubmitting
```

Those values are reactive, so templates can consume them without maintaining a second copy of form state.

For example:

```vue
<template>
  <button
    type="submit"
    :disabled="form.isSubmitting"
  >
    {{ form.isSubmitting ? 'Submitting…' : 'Submit' }}
  </button>
</template>
```

Read more in [Form state](/docs/concepts/form-state).

## Dynamic arrays

Repeatable fields need more than `push()` and `splice()` because field state also needs to follow the data.

[`ArrayField`](/docs/components/array-field) provides:

```text
append  prepend  insert  remove  update  swap  move
```

Each item has a stable `key` for rendering and a `path` for connecting nested fields. Array mutations keep item keys aligned and remap nested touched state and validation issues with the corresponding items. Dirty state is derived by comparing current values with the reset baseline, so it reflects the values at their current paths after a reorder.

Read more in [Dynamic arrays](/docs/concepts/arrays).

## Vue 3 and Nuxt

The core package works directly in Vue 3. The official `@notform/nuxt` module adds Nuxt integration and auto-imports `useForm`, `Form`, `Field`, `ArrayField`, and `Error`. The module also lets you alias selected auto-import names through `notform.aliases`.

The form behavior is the same in both environments.

Read more in [Nuxt](/docs/getting-started/nuxt).

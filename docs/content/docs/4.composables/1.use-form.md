---
title: useForm
description: Create and manage a typed, reactive NotForm form instance.
---

`useForm()` creates the form instance used by NotForm's components and composables.

It connects a Standard Schema-compatible validator to reactive values, errors, interaction state, validation, submission, and reset behavior.

## Usage

```ts
import { useForm } from 'notform'
import { z } from 'zod'

const schema = z.object({
  email: z.email(),
  password: z.string().min(8),
})

const form = useForm({
  initialValues: {
    email: '',
    password: '',
  },
  async onSubmit(values) {
    await save(values)
  },
  schema,
})
```

## Signature

```ts-type
useForm<TSchema extends ObjectSchema>(
  settings: FormInstanceSettings<TSchema>,
): UseFormReturn<TSchema>
```

## Options

| Option | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `schema` | `MaybeRefOrGetter<TSchema>` | Yes | — | Standard Schema validator; accepts a schema value, ref, or getter |
| `initialValues` | `DeepPartial<InferInput<TSchema>>` | No | `{}` | Starting values and the dirty/reset baseline; deeply cloned |
| `initialErrors` | `Issue[]` | No | `[]` | Initial active issues and the error baseline restored by `reset()` |
| `onSubmit` | `(data: InferOutput<TSchema>) => Promise<void> \| void` | No | — | Called with validated schema output after successful submit validation |

## Return value

### Values and errors

| API | Type | Description |
| --- | --- | --- |
| `values` | `DeepPartial<InferInput<TSchema>>` | Deeply reactive input values |
| `errors` | `Issue[]` | Current active validation issues |
| `getFieldErrors(path)` | `Issue[]` | Issues whose normalized path exactly matches `path` |
| `setError(error)` | `void` | Add an issue or replace the issue at the same normalized path |
| `setValue(path, value)` | `void` | Set a typed field value without automatically validating |

### State

| API | Type | Description |
| --- | --- | --- |
| `isDirty` | `boolean` | Whether current values differ from the reset baseline, using deep comparison |
| `isTouched` | `boolean` | Whether any path was touched or the form has been submitted |
| `isValid` | `boolean` | Whether `errors` is empty; it does not run validation |
| `isValidating` | `boolean` | Whether a validation run is active |
| `isSubmitting` | `boolean` | Whether a submit attempt is currently in progress |
| `isSubmitted` | `boolean` | Whether at least one submit attempt has been accepted since the last reset |
| `submitCount` | `number` | Number of accepted submit attempts since the last reset |

`isSubmitted` also affects field and array touched state: after a submit attempt, their `isTouched` flags report `true` until the form is reset.

### Validation and lifecycle

| API | Type | Description |
| --- | --- | --- |
| `validate()` | `Promise<StandardSchemaV1.Result<InferOutput<TSchema>>>` | Validate the whole form and replace the error collection if the result is current |
| `validateField(path)` | `Promise<StandardSchemaV1.Result<InferOutput<TSchema>>>` | Validate the schema and update only issues within the requested path subtree |
| `submit(event?)` | `Promise<void>` | Prevent a supplied native event, validate, then call `onSubmit` when valid |
| `reset(values?, errors?)` | `void` | Replace optional reset baselines, restore values/errors, and clear interaction/submission state |

## `values`

Values use the schema's input type:

```ts
form.values.email = 'jane@example.com'
```

The object is deeply reactive and can be bound directly with `v-model`.

## `setValue`

Use `setValue()` when a custom input or application code needs to update a field:

```ts
form.setValue('email', 'jane@example.com')
```

The path and value are inferred together from the schema.

Calling `setValue()` updates the reactive value and derived dirty state, invalidates older in-flight validation, and does **not** run validation itself. Direct `v-model` or nested mutations also invalidate in-flight validation.

## `errors`

`form.errors` is the shared collection used by the form and field components.

Use `getFieldErrors()` for an exact path:

```ts
form.getFieldErrors('email')
```

A nested descendant issue is not returned by a parent exact-path query. Array-field aggregate state can still account for descendant issues.

## `setError`

Use `setError()` for server-side errors or application-specific validation:

```ts
form.setError({
  message: 'Email is already registered.',
  path: ['email'],
})
```

A second issue at the same normalized path replaces the previous one. An issue without a path can represent a form-level error.

## `validate`

```ts
const result = await form.validate()
```

A successful current validation clears current errors and returns the schema output. A failed current validation returns issues and replaces `form.errors`.

If values or the schema change during an asynchronous validation, that result is treated as stale and cannot overwrite the shared error state. When whole-form validations overlap, only the latest current run can commit its result.

## `validateField`

```ts
await form.validateField('email')
await form.validateField('users')
await form.validateField('users.0')
```

Parent object and array paths include descendant issues in the validation scope. The validator still runs against the form's current schema and full values; only the shared errors written by this call are scoped to the requested path subtree.

The returned value remains the full schema result, not a field-only output.

## `submit`

When using `<Form>`, the component automatically calls `form.submit()` for native submit events:

```vue
<template>
  <Form :form="form">
    <!-- fields -->
    <button
      type="submit"
      :disabled="form.isSubmitting"
    >
      {{ form.isSubmitting ? 'Submitting…' : 'Submit' }}
    </button>
  </Form>
</template>
```

You can also call it directly:

```ts
await form.submit()
```

A native event is prevented immediately. A submit attempt increments `submitCount` and sets `isSubmitted`; a second submit while `isSubmitting` is already true is ignored. The form then validates its full values, stores validation issues when invalid, and calls `onSubmit` with schema output only when validation succeeds.

## `reset`

Reset the current baseline:

```ts
form.reset()
```

Or establish a new baseline:

```ts
form.reset({
  email: 'jane@example.com',
})
```

You can also provide baseline errors:

```ts
form.reset(
  { email: 'jane@example.com' },
  [{ message: 'Verification required', path: ['email'] }],
)
```

`reset()` restores the baseline values and errors, clears explicit touched state and the submit count, invalidates in-flight validation, and releases the current submission state. It cannot abort external async work that has already started inside `onSubmit`. When called with a native reset event, the event is ignored and the existing baseline is restored; `<Form>` already wires this behavior for you.

::caution
`reset(values, errors)` replaces the supplied baselines. A provided values object is not merged with the previous baseline, so keys omitted from the replacement are removed.
::

## Input and output types

The form instance uses two related schema types:

```text
InferInput<TSchema>   → form.values / initialValues
InferOutput<TSchema>  → validate result / onSubmit
```

This distinction matters for schemas that coerce or transform data during validation.

## Reactive schema

`schema` accepts a value, a Vue ref, or a getter through `MaybeRefOrGetter`:

```ts
const form = useForm({
  schema: computed(() => currentSchema.value),
})
```

Changing the reactive schema invalidates in-flight validation. The validator remains external to NotForm and is never turned into a NotForm-specific schema object.

---
title: Dynamic Arrays
description: Build repeatable fields while keeping item identity and nested state in sync.
---

Arrays are where ordinary reactive state and form state can easily drift apart.

Removing or reordering an item changes positions, but touched fields, dirty markers, validation errors, and rendered component identity also need to follow the item that moved.

[`ArrayField`](/docs/components/array-field) handles that bookkeeping.

## Stable item identity

Each item exposes:

```ts
{
  key: string
  index: number
  path: string
}
```

Use `item.key` for the Vue key:

```vue
<template>
  <div
    v-for="item in items"
    :key="item.key"
  >
    ...
  </div>
</template>
```

The index describes the item's current position. The key represents its identity within the field instance.

## Mutations

| Method | Behavior |
| --- | --- |
| `append(value)` | Add to the end |
| `prepend(value)` | Add to the beginning |
| `insert(index, value)` | Insert at a normalized position |
| `remove(index)` | Remove an existing item |
| `update(index, value)` | Replace an item without changing its key |
| `swap(indexA, indexB)` | Exchange two items |
| `move(from, to)` | Move an item to a destination |

Use these methods instead of mutating the array directly.

## Nested state follows the item

For a field such as:

```text
users.0.profile.email
```

moving user 0 to index 2 remaps the associated touched state and validation issues to:

```text
users.2.profile.email
```

The same rule works through nested arrays. Dirty state is computed by comparing current values at each path with the reset baseline; it is not stored as item metadata, so dirty flags may change after a reorder as values occupy different positions.

## Why direct mutation is discouraged

Avoid:

```ts
form.values.users.push(user)
form.values.users.splice(index, 1)
```

Those operations change the values but bypass the array field's key bookkeeping and state remapping.

Use the renderless mutation methods instead:

```ts
append(user)
remove(index)
move(index, 0)
```

## `itemSchema`

`itemSchema` is an optional prop used for TypeScript inference when the item type cannot be inferred from the surrounding expression.

It is not a second runtime validator. Items are still validated through the main form schema.

## Aggregate state

`ArrayField` exposes recursive aggregate state:

- `isValid`
- `isTouched`
- `isDirty`
- `isValidating`

An issue anywhere under the array makes `isValid` false. A touched or dirty descendant makes the corresponding aggregate state true.

The `errors` slot prop remains exact-path: it contains issues reported directly on the array path, such as an array-level minimum-length rule.

## External replacement

Replacing the whole array through `form.setValue()` is supported, but arbitrary replacement data cannot carry existing item identity with it.

`ArrayField` keeps its key list aligned with the new length. For edits that need to preserve row identity, use the mutation methods.

## Index rules

Existing-item mutations ignore invalid indices rather than creating sparse arrays or changing unrelated state.

`insert()` normalizes its insertion position. `move()` normalizes the destination. `remove()`, `update()`, and `swap()` require valid existing indices.

## Async validation and mutations

A structural array mutation invalidates older in-flight validation results. Array dirty state is derived from the current array value compared with its reset baseline, so it updates automatically after each mutation.

This is what prevents a stale async result from appearing on a new row after a remove, insert, swap, or move.

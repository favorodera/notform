NotForm treats validation as a boundary between your form state and your schema.

The schema decides whether data is valid. NotForm decides when validation runs, how issues are stored, and which result is allowed to update shared state.

## Standard Schema

The `schema` passed to `useForm()` implements the [Standard Schema](https://standardschema.dev/) contract and accepts an object as its input.

This keeps NotForm independent of any particular validator.

```ts
import { z } from 'zod'

const schema = z.object({
  email: z.email('Enter a valid email'),
})

const form = useForm({
  schema,
})
```

## `validate()`

`form.validate()` runs the schema against the complete form.

```ts
const result = await form.validate()

if (result.issues) {
  console.log(result.issues)
} else {
  console.log(result.value)
}
```

When validation fails, the returned issues replace `form.errors`.

When validation succeeds, current form errors are cleared and the schema's output value is returned.

## `validateField()`

`form.validateField(path)` runs the current schema while scoping the resulting issues to the requested path.

```ts
await form.validateField('email')
```

A path can describe different levels of the form:

```ts
await form.validateField('profile.email')
await form.validateField('profile')
await form.validateField('users')
await form.validateField('users.0')
```

For object and array scopes, descendant issues belong to that scope.

For example, validating `users` can return an issue at `users.0.email`.

This is different from `getFieldErrors()`, which is deliberately exact-path matching.

## Validation triggers

`Field` controls automatic validation through `validateOn`.

| Trigger | Behavior |
| --- | --- |
| `onBlur` | Validate when the field loses focus |
| `onChange` | Validate from the change handler |
| `onInput` | Validate from the input handler |
| `onMount` | Validate once after mount |

The defaults enable blur and change validation; input and mount validation are opt-in:

```ts-type
{
  onBlur: true,
  onChange: true,
  onInput: false,
  onMount: false,
}
```

The configuration is merged over these defaults, so you can override one trigger without redefining the others. `onMount` runs automatically after mount when enabled and is not included in the `events` slot object. The blur handler marks the path touched even when blur validation is disabled.

`validationMode` controls whether input and change handlers trigger validation.

### Eager

In `eager` mode, enabled `onInput` and `onChange` triggers run validation whenever those handlers fire. This is the default mode.

### Lazy

In `lazy` mode, input and change validation are suppressed even if their triggers are enabled in `validateOn`. Blur validation remains available when `onBlur` is enabled, as do explicit `validateField()` and `validate()` calls. The default is `eager`.

## Debouncing

Use `debounce` when input or change validation should wait for a pause in typing.

```vue
<template>
  <Field
    path="username"
    :debounce="300"
  >
    ...
  </Field>
</template>
```

Only input/change validation is delayed. When `onBlur` is enabled, blur validation runs immediately and cancels a pending debounced validation.

## Async validation

A Standard Schema validator can return a promise, which makes async rules possible.

Examples include checking username availability, validating a remote address, or running any other rule that depends on a request.

NotForm exposes the lifecycle through `isValidating` and protects shared state from stale async results.

## Concurrent validation

Whole-form validation uses last-write-wins semantics for shared `form.errors`.

Each call still resolves with its own validator result, but an older whole-form call cannot overwrite the state produced by a newer run.

Field validation adds a per-path cycle so a newer validation of the same field supersedes an older one.

Changing values while validation is in flight also invalidates the older run. The same protection applies to array mutations, preventing an old result from being written against a different item after a reorder or removal.

## What counts as an error?

Standard Schema issues can have no path, a field path, or a nested path.

Pathless issues belong to the form as a whole:

```ts
form.setError({
  message: 'Unable to save your changes.',
})
```

Field queries remain precise:

```ts
form.getFieldErrors('email')
```

Array aggregate state is intentionally broader and includes descendants.

## Validation and UI state

Validation does not decide when your UI should show an error.

A common pattern is to combine touched state and errors:

```vue
<template>
  <Field
    v-slot="{ errors, isTouched }"
    path="email"
  >
    <!-- <input ...> -->

    <p v-if="isTouched && errors.length > 0">
      {{ errors[0].message }}
    </p>
  </Field>
</template>
```

Or use [`Error`](/docs/components/error) for the common first-error case.

## API comparison

| API | Scope | Writes to `form.errors` | Typical use |
| --- | --- | --- | --- |
| `validate()` | Whole form | Entire error collection | Submit or full validation |
| `validateField(path)` | Requested path and descendants | Matching scope | Field-level validation |
| `getFieldErrors(path)` | Exact path only | No | Reading field errors |
| `isValid` | Current form | No | Rendering state |
| `isValidating` | Active validation runs | No | Loading state |

Continue with [Submission](/docs/concepts/submission) for the submit lifecycle.
